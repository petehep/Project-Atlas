1. Executive Summary

This Interface Control Document (ICD) defines the complete interface specification between the ATLAS Master Flightline Clock software system and the physical LED matrix display hardware used at competitive aviation events. The document governs all aspects of the display interface: physical panel selection and mounting, electrical signal definitions, communication protocols, software abstraction architecture, and integration requirements.

The ATLAS system currently operates in a software-simulator mode, where AtlasLEDSimulator renders the 6-row display layout in a Qt6 window on the host Mac Mini M4. This ICD establishes the architectural framework and technical specifications needed to transition from the current simulator to physical LED panel hardware, without requiring changes to the core timing engine or operator console.

Scope of Interface Control

This ICD has authority over the following interface boundaries:

  • Software-to-Hardware boundary: The DisplayBackend abstract class defines the contract between the AtlasEngine and any physical or simulated display hardware.
  • Electrical interface: HUB75 signal levels, timing, connector pinout, and power distribution between the host controller and LED panels.
  • Mechanical interface: Panel dimensions, mounting provisions, and cabling topology.
  • Operational interface: Brightness control, on/off sequencing, and fault behaviour during heat operations.
Note — Modular ICD Approach
Sections describing electrical pin-level specifications and mechanical dimensions are currently defined generically for the P5/P10 panel family. Hardware-specific values (exact panel model number, controller board, wiring harness part numbers) shall be inserted in a Rev 1.1 update once hardware procurement is finalised.

Key Design Decisions Codified in This Document

  1. The 6-row display layout is the normative rendering target for all physical hardware; it is not a simulator artefact.
  2. The Hardware Abstraction Layer (HAL) isolates all hardware-specific code; no HAL code shall appear in the engine, models, or operator console modules.
  3. HUB75 is the primary protocol for direct-drive Raspberry Pi / FPGA controller implementations. Artnet DMX and Serial/UART are documented as secondary options for network-based or embedded controller alternatives.
  4. Brightness control (10–100%) is a first-class operational requirement and must be implementable on all backends without restarting the application.

2. System Overview

ATLAS (Automated Timing & LED Announcement System) is a Master Flightline Clock designed for competitive aviation events such as Race to the Sky and similar airshow circuits. It provides a single authoritative time reference for track operations, driving both the operator console (internal) and a large-format public LED display (external, visible to pilots and spectators).

2.1 Architecture Context

The system runs on a Mac Mini M4 and implements a strict Model-View-Controller (MVC) architecture. The display subsystem is intentionally isolated from the timing engine via a well-defined data model boundary. 4. Interface Protocols

4.1 HUB75 RGB LED Matrix Protocol

HUB75 is the de facto standard parallel interface for driving RGB LED matrix panels directly from a microcontroller or single-board computer. It uses a 16-pin IDC (2×8) connector and transmits pixel data serially, one row at a time, using a shift-register architecture. The protocol is synchronous: all signals are referenced to a common clock (CLK).

The HUB75 protocol drives two rows simultaneously per clock cycle (upper half and lower half of the panel are driven in parallel via separate R1/G1/B1 and R2/G2/B2 data lines). For a 32-row panel, the row select lines A, B, C, D address 16 pairs, yielding 16 multiplex steps per frame.

HUB75E Variant
HUB75E adds a fifth row-select line (E) to support 64-row panels (32 pairs). P5 modules commonly use HUB75E. The ATLAS HAL must detect the panel height and configure the row-select bus accordingly (4-bit for 32-row, 5-bit for 64-row).

4.2 Alternative Protocols

4.2.1 Artnet DMX (UDP/IP)

Artnet is an Ethernet-based protocol that encapsulates DMX512 data in UDP packets, transmitting pixel values over a standard network switch. It is supported by commercial LED controllers (e.g., Novastar, Colorlight) and is appropriate when the host computer and LED controller are connected via Ethernet rather than GPIO/USB. Artnet Universe 0, starting at DMX address 1, can carry 512 channels, sufficient for a 64×64 display as 8-bit RGB (512/3 = 170 pixels per universe; chained universes required for larger arrays).

4.2.2 Serial / UART

A simplified serial protocol over USB-to-UART or RS-232 is viable for custom or low-cost embedded controllers. A text-based or binary frame structure (see Section 5.3) can be transmitted from the Mac Mini at 115,200 baud or higher. This approach requires a custom firmware image on the controller board and is the least mature of the three protocol options. It is included for completeness and for scenarios where Ethernet and GPIO both present integration challenges.

5.3 Data Frame Format

The ATLAS HAL represents a complete display frame as a two-dimensional byte array of dimensions [height][width][3], where the innermost dimension contains the R, G, B byte values (8-bit per channel). Brightness scaling is applied by the HAL before transmission; the engine and model layers always operate in full-scale (0–255) colour.

# Frame buffer type definition (Python pseudo-specification)
FrameBuffer = List[List[Tuple[int, int, int]]]   # [row][col] = (R, G, B)

# Dimensions: frame[row][col] where
#   row in range(0, display_height)   # 0 = top
#   col in range(0, display_width)    # 0 = left
#   R, G, B in range(0, 256)          # full 8-bit colour, pre-brightness-scaled

# Example: set pixel at row=5, col=10 to full red
frame[5][10] = (255, 0, 0)

# Brightness application before HAL send:
scaled = tuple(int(ch * brightness / 100) for ch in (R, G, B))

5.4 Row Addressing for 6-Row Configuration

It is important to distinguish between the logical display rows defined by the ATLAS 6-row layout strategy (Section 2.3) and the physical row scan lines of the HUB75 panel. The 6-row layout refers to content regions defined in pixel coordinates; the HUB75 panel scans each physical pixel row independently. Figure 5-2 maps logical rows to physical pixel rows for the Full profile (128×64).

Note — No Software Row Mapping Required
The rpi-rgb-led-matrix library abstracts away the physical scan pairs; software writes to a 2D pixel coordinate space and the library handles interleaving. Direct register-level implementations must account for the pair interleaving shown in Figure 5-2.

6. Hardware Abstraction Layer (HAL)

The Hardware Abstraction Layer is the critical architectural boundary between the ATLAS application software and the physical display hardware. All hardware-specific code is contained within backend modules that implement the DisplayBackend abstract interface. No hardware-specific code shall appear in engine.py, models.py, windows.py, or database.py.

6.1 Abstract Interface Design

The DisplayBackend abstract base class defines the complete contract that every backend must fulfil. It consists of five mandatory methods. Any class that does not implement all five methods cannot be registered as a valid backend.

from abc import ABC, abstractmethod
from core.models import AtlasDisplayModel

class DisplayBackend(ABC):
    """
    ATLAS HAL — Abstract Display Backend (ATLAS-ICD-001 §6.1)
    All physical and virtual display implementations must inherit
    from this class and implement every abstract method.
    """

    @abstractmethod
    def initialize(self, config) -> bool:
        """
        Allocate hardware resources, open device handles, and configure
        the display for operation.
        :param config: DisplayConfig object (width, height, brightness, etc.)
        :return: True if initialisation succeeded; False on failure.
        """

    @abstractmethod
    def render(self, model: AtlasDisplayModel) -> None:
        """
        Receive an AtlasDisplayModel snapshot and render a complete frame
        to the display. Called once per engine tick (≈1 Hz).
        Must NOT block for more than 100 ms.
        """

    @abstractmethod
    def set_brightness(self, value: int) -> None:
        """
        Adjust display brightness in real time.
        :param value: Integer percentage, range 10–100 inclusive.
        Must take effect within 2 seconds without restarting the app.
        """

    @abstractmethod
    def clear(self) -> None:
        """
        Set all pixels to off (black). Called on graceful shutdown
        to blank the display before power-down.
        """

    @abstractmethod
    def shutdown(self) -> None:
        """
        Release all hardware resources. Called once on application exit.
        Must call clear() before releasing resources.
        """

6.3 Physical Hardware Backend (Future)

The HUB75Backend will be implemented to drive physical LED panels via a Raspberry Pi controller. The Mac Mini communicates with the Raspberry Pi over a local TCP socket (preferred) or USB-Serial link. The Raspberry Pi runs a lightweight Python daemon (atlas_display_daemon.py) that accepts AtlasDisplayModel JSON objects, renders the 6-row frame using the rpi-rgb-led-matrix Python bindings, and writes directly to the HUB75 GPIO bus.

The ArtnetBackend is an alternative future backend for installations using a commercial LED controller connected to the venue Ethernet infrastructure. It packages the rendered frame buffer as Artnet universe packets and transmits them via UDP broadcast to the controller's IP address.

6.4 Backend Selection Mechanism

The backend is selected at application startup from the display_backend key in the ATLAS settings database. The backend factory module returns a fully configured backend object ready for initialize() to be called. No restart is required to switch brightness; a restart is required to switch backend type.

# backend_factory.py  (ATLAS-ICD-001 §6.4)
BACKEND_REGISTRY = {
    "simulator": SimulatorBackend,
    "hub75":     HUB75Backend,      # Future
    "artnet":    ArtnetBackend,     # Future
    "serial":    SerialBackend,     # Prototype
}

def create_display_backend(backend_type: str) -> DisplayBackend:
    cls = BACKEND_REGISTRY.get(backend_type)
    if cls is None:
        print(f"[WARN] Unknown backend '{backend_type}', falling back to simulator")
        cls = SimulatorBackend
    return cls()

Warning — Power Sequencing
Always power the LED panels before asserting HUB75 data signals. Applying data signals to unpowered panels may damage input protection diodes. The ATLAS shutdown procedure must clear (blank) the display before cutting panel power.

7.2 Cabling and Connectors

  • Panel power cable: 5 V / 0 V on 14 AWG (≥2.5 mm²) minimum for runs up to 1 m. Voltage drop shall not exceed 0.2 V at peak load. Use star-topology power distribution from the PSU to each panel module.
  • HUB75 data cable: Standard 16-pin IDC flat ribbon cable. Maximum recommended length between controller and first panel: 0.5 m. Between daisy-chained panels: use panel's built-in pass-through connector; do not extend with additional cable.
  • Controller-to-host cable (Raspberry Pi option): Standard USB-A to USB-Micro or USB-C, maximum 2 m, or shielded Cat-5e Ethernet for TCP socket connection, maximum 100 m.
  • Grounding: The signal ground of the HUB75 connector (pins 4 and 8) must be bonded to the PSU negative rail and to the panel chassis. A single-point ground at the PSU is preferred.

7.4 Safety and Compliance

The following electrical safety and EMC requirements apply to the complete ATLAS display installation:

  • All power supplies must carry an applicable safety certification for the jurisdiction of use (e.g., SAA/RCM for Australia/NZ, CE for EU, UL for USA/Canada).
  • The installation must comply with AS/NZS 3000 wiring rules (Australia/NZ) or the applicable national electrical code.
  • LED display panels are Class 1 equipment; the panel chassis shall be protectively earthed (green/yellow conductor, minimum 1.5 mm²).
  • EMC emissions from the HUB75 flat ribbon cable can be significant. Cable shall be routed away from RF-sensitive equipment (e.g., radio receivers, GPS units). Ferrite clamps on the ribbon cable at both the controller and panel ends are recommended for P10 outdoor installations.
  • A residual current device (RCD/GFCI) of 30 mA or less shall protect the AC supply circuit feeding the display PSU, per AS/NZS 3000:2018 requirements for outdoor electrical equipment.

8.2 Acceptance Criteria

The ATLAS display hardware integration is accepted when all ten IVT tests pass with zero failures in a single test run. A partial pass (nine of ten) is not acceptable; all tests are mandatory. The test results shall be documented on an IVT sign-off sheet referencing this document (ATLAS-ICD-001 Rev 1.0) and retained as part of the project commissioning record.

The following quantitative performance requirements constitute the minimum acceptance threshold for physical hardware:

  • Frame render latency from model receipt to first pixel visible: ≤ 100 ms
  • Brightness adjustment response time: ≤ 2 seconds
  • Panel refresh rate (hardware scan rate): ≥ 60 Hz (P10), ≥ 120 Hz (P5)
  • Dead pixel count: 0 (zero tolerance; any dead pixel requires panel replacement)
  • Operational uptime during a six-hour competition day: ≥ 99.5% (maximum 108 s of unplanned outage)

Appendix A — Glossary of Terms

Artnet DMX
An industry-standard protocol encapsulating DMX512 lighting control data in UDP/IP packets for transmission over Ethernet networks.
AtlasDisplayModel
The Pydantic data model class in models.py that carries all display-relevant state from the AtlasEngine to the HAL backend once per second.
AtlasEngine
The core timing state machine in engine.py. Maintains phase P0–P4 transitions, UTC-referenced countdown timers, and auto-activation of heats.
Compact Mode
The six-row display layout profile selected when display width ≤ 96 px. Uses abbreviated phase labels and single-scale font throughout.
DisplayBackend
The abstract base class (ATLAS HAL) that all display implementations must inherit. Defines the initialize, render, set_brightness, clear, and shutdown interface contract.
Full Mode
The six-row display layout profile for display width > 96 px (e.g., 128×64). Uses 2× scaled primary timer font and inline track window times.
HAL
Hardware Abstraction Layer. The architectural boundary in ATLAS that isolates application software from hardware-specific display drivers.
HUB75
A 16-pin IDC parallel interface standard used to drive RGB LED matrix panels. The primary approved protocol for ATLAS physical hardware integration.
HUB75E
An extended variant of HUB75 adding a fifth row-select line (E) to support panels with 64 or more rows, such as P5 indoor panels.
ICD
Interface Control Document. A formal engineering document defining the interface between two subsystems or components.
IDC
Insulation-Displacement Connector. A cable connector type that terminates multi-conductor flat ribbon cables by piercing the insulation.
OE
Output Enable. An active-LOW signal on HUB75 that gates the LED driver outputs. PWM modulation of OE controls display brightness.
P5
A 5 mm pixel pitch LED panel type, typically SMD-packaged, recommended for indoor or short-viewing-distance applications.
P10
A 10 mm pixel pitch LED panel type, typically available in outdoor-rated (IP65) configurations, recommended for flight line and grandstand deployments.
Phase (P0–P4)
The five operational states of the ATLAS timing engine relative to the current heat's track_open, track_close, and heat_end timestamps.
PSU
Power Supply Unit. Provides regulated 5 V DC power to LED panel modules.
PWM
Pulse-Width Modulation. Technique used to control LED brightness by rapidly switching power at varying duty cycles.
RCD
Residual Current Device (also RCCB or GFCI). A safety device that disconnects the AC supply if it detects current leakage to earth.
rpi-rgb-led-matrix
An open-source C/Python library by Henner Zeller for driving HUB75 LED panels directly from Raspberry Pi GPIO.
STB / LAT
Strobe / Latch. A HUB75 signal that transfers the contents of the shift register to the LED driver output latches, making a new row of pixels visible.
